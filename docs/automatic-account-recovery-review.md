# Automatic Collection and settings recovery

A fresh phone could see cloud activities but not its cloud-only Collection or backed-up preferences. Removing the manual Restore control left `restoreCloudJournal` without a production caller. Automatic backup then attempted to upload fresh defaults before reading the existing settings baseline.

`AutoCloudSync` now reads owner-only Collection/settings records before their first upload on each signed-in launch. Missing Collection items are added within the existing 50-item device limit. Existing local items, queued removals, local notification permission and acknowledged settings remain authoritative. Settings recovery merges missing values and saved lists; a distance-unit edit made during recovery is preserved. Revision receipts are adopted for newly recovered records, never fabricated for an existing conflicting local Collection edit. AuthContext's queued functional preference updates preserve changes made during the read; owner guards reject delayed account-switch work.

Missing Collection photos download automatically in batches of four, with ten-second network limits and the existing image size bound. Their base64 SHA-256 must match the read cloud row. A failed or changed photo remains pending; its object key and hash survive the native preferences bridge. Backup retains that reference while the photo is absent locally, preventing a failed download from erasing the cloud reference. A later automatic pass retries. A local photo chosen during recovery takes precedence.

Recovery is additive: it does not uninstall an app, clear storage, delete cloud data, rewrite recorded activities or upload routes for a preference change. If the read fails, settings/Collection uploads wait, while activity backup and journey metadata refresh still proceed. Existing cloud activity lists and on-demand cloud photo reads remain the path for activity history; this change does not eagerly duplicate all route history onto a new phone.

Code review covered account changes, native persistence, concurrent edits/removals, optimistic cloud revisions, photo integrity and bounded retry. No new schema, RLS policy, backend deployment or user-specific database repair is required. This closes the previously identified missing Collection/settings recovery path. Physical replacement-phone and outdoor Watch behavior remain beta validation tasks; automated tests are not evidence those device trials occurred.
