# Authentication and onboarding — build 1.0 (3)

## Implemented application behavior

Private Home, Map, Record, Trips, Garage/Tesla, household, profile/settings and local photos require an authenticated, email-confirmed account. `AuthProvider` is the only session manager. The private tree does not mount during restoration, sign-out, reauthentication, recovery or account deletion. Deliberately public `?journey=TOKEN` pages remain accessible without login and read only the detached server projection.

The first launch opens a dedicated Welcome screen. Email/password registration/login, confirmation messaging, recovery email, native recovery callbacks, password update, session restoration and sign-out use the existing Supabase client/project. There is no demo login, bypass or fake Apple identity. Supabase auth callbacks defer follow-up requests to avoid its session lock; app visibility/lifecycle resumes token refresh without tying native GPS collection to JavaScript.

Native Apple Sign In uses AuthenticationServices, a cryptographic nonce hashed with SHA-256, state validation and Supabase `signInWithIdToken`. Full name is captured when Apple provides it. The application also retains strict, idempotent PKCE callback handling for email links and browser OAuth. Callback failures are retryable; duplicate cold/warm callbacks are suppressed. Apple authorization codes go only to a signed-in server endpoint for identity-checked exchange and encrypted refresh-token retention, supporting later Apple revocation. This code is disabled until external configuration is complete.

After authentication, six saved stages cover profile/name/optional photo, optional private Home, optional automatic history/permissions, optional Tesla/manual vehicles, optional household and completion. Home reuses native address search, map positioning, radius editing and explicit current-position confirmation. Location and motion requests occur contextually, and automatic status says verified only after a recent native GPS fix. Manual recording does not request new motion permission just for a user-selected activity. Vehicle/household setup can be skipped. Returning users bypass onboarding once complete.

Profile, vehicles and progress are stored per account. Display name/progress also use the caller's Supabase Auth metadata so no new schema is needed for that basic setup. Native profile photographs are cropped/re-encoded and retained privately on this device; cross-device avatar upload is not implemented. Household RPCs read the confirmed member's name from owned preferences or Auth metadata, not email/private location.

## Local account security and GPS

- Supabase sessions/refresh tokens and PKCE verifiers use device-only Keychain storage on iOS. Legacy WebView auth values migrate to Keychain and are removed after acknowledgement. Native bridge logging is disabled so session tokens are not printed by Capacitor.
- Each verified user has a separate Application Support directory and random AES-256-GCM key held only in Keychain. Trips, GPS, photos, places, preferences and tombstones are encrypted. File data protection permits writing while locked after first unlock. Native `bindAccount` independently validates the token against the fixed Letm3go Auth endpoint and checks confirmed email/user ID.
- Offline reopening is limited to a previously verified active account. A different account cannot bind offline. A temporary network/refresh failure preserves local GPS. A revoked/rejected session locks the UI and stops private native collection while retaining saved data.
- Native background recording can restore the trusted persisted account without a running WebView. Its UI remains locked until auth restoration/binding succeeds. Explicit sign-out stops location, visits, region monitoring and motion, saves pending work and clears the active binding. Another account cannot read that user's encrypted files, media, preferences or vehicle history.
- Account transitions reject stale asynchronous bindings and photo callbacks. Private photos are decrypted through an owner-checked native method; raw file URLs/paths are not returned. A new account's automatic detection excludes queued GPS fixes from before its binding boundary.
- Earlier pre-authentication recordings and photo files are preserved in an encrypted **unassigned** quarantine. Earlier unscoped vehicle/bookmark preferences are preserved there too. They are not automatically assigned to the next account. A reviewed ownership/recovery procedure is still needed to import that older anonymous history. Signing in will initially show only this account's assigned records.
- If the device cannot checkpoint pending data (for example full storage), it stops collection and reports failure rather than claiming successful sign-out/saving. First-unlock and iOS force-quit/system termination restrictions still apply. Long-session storage I/O and large legacy-migration timing need physical profiling.

The browser uses per-user preference namespaces and standard Supabase browser session storage. It does not provide native GPS or the iOS Keychain/encrypted-files guarantees.

## Prepared backend and connected services

`20261024020000_auth_onboarding_households.sql` adds owner-scoped setup records; household creation, single-use expiring invitations, joining/member listing/leave and ownership succession; live-session-bound APNs registration; and service-only encrypted provider credentials/OAuth states. Joining grants no historical trip or live-location access. Confirmed household contact relationships support later explicit per-trip grants; leaving revokes that relationship. Client roles cannot set membership/roles, read APNs/provider secrets or forge another push owner. Auth-account deletion cascades owned records without resurrecting owner tombstones.

`functions/account` verifies the caller and recent authentication before deletion. It revokes Apple tokens, requires Tesla consent/disconnection first, freezes new media/connections, revokes publication, removes owner-prefixed R2 media in bounded batches, deletes the Auth user and cleans queued keys. Large/incomplete cleanup returns pending/error; the client never treats that as confirmed deletion. Deletion intent is server-controlled and locks normal UI on reconnection. Local confirmed cleanup cryptographically erases that account's key and removes its files. A network failure after a server-side deletion can require local cleanup/recovery review; this destructive workflow needs staging/live validation before release.

`functions/tesla` implements authenticated consent initiation, expiring one-use state, an HTTPS callback, official code exchange and encrypted per-user token storage. Vehicle listing/selection is additionally blocked unless the operator approves Fleet API reads/costs. Garage validates official Tesla URLs, allows explicit location consent and selects only vehicles returned for that caller. Sign-out does not revoke Tesla. Consent revocation follows Tesla's documented interactive page; disconnect checks that a refresh grant is no longer usable before clearing credentials. Automatic refresh, telemetry hosting and journey ingestion remain unimplemented. None of these live Tesla operations were executed.

Push adapts ImBored's contextual permissions and account/installation lifecycle. A granted prior opt-in can re-register without prompting. Logout unregisters local notifications/listeners and removes delivered items. SQL ownership/session checks prevent late callbacks from binding a previous user's token under a new account. `eligible_push_devices` excludes revoked sessions. Actual APNs sending, event production and notification navigation/inbox are not implemented or verified. Future notification payloads must contain only generic text/opaque event IDs, with private content fetched after authentication.

## Device acceptance sequence

Install build 3, create an account, open its confirmation email, sign in, choose a profile, optionally save Home, grant/decline automatic history, add a manual vehicle and optionally create/join a household after approved deployment. Complete onboarding and relaunch: it should restore Home without repeating setup. Record/lock/offline/reopen and verify the journey persists under this account. Sign out during pending work: collection should stop and account data disappear from normal UI. Sign in as a second account and verify no first-account trips, photos, places, vehicles or profile appear. Restore the original account online and recover its pending activity. Test revoked/expired sessions separately from offline refresh failures. Test real password recovery and Apple sign-in/deletion after external setup. Verify household joining exposes no historical GPS and account deletion cleans R2/Auth/local stores in staging before release.
