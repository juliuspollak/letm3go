# Tesla automatic recording pilot

## Production audit

20 November 2026, Sydney. Read-only checks against the linked Supabase project showed `tesla` active at version 5. `tesla-recording` and `telemetry-ingest` were absent. A request to the recording endpoint returned the platform's function-not-found response. The refresh-lease and Fleet Telemetry migrations are recorded as applied. The database has one connected Tesla account and **one imported Tesla**, up from zero imports on 19 November. The import is evidence discovery and selection worked at least once. A read-only download of the deployed OAuth source confirmed it omits VINs and granular location privacy from the discovery cache. That version can import a Collection item, but the recording function cannot bind it. Deploy the repository's VIN-capable OAuth function with its existing credentials, then refresh discovery. Current grants and token refresh still require an authorized live check.

There are zero bindings, zero fleet events, zero Tesla activities and no recorded receiver heartbeat. The proposed `fleet.letm3go.au` hostname returned no DNS address. The six existing Tesla/OAuth keys are listed by name, including `TESLA_API_READS_APPROVED`. No `FLEET_*` project secrets were listed. Secret values, provider billing, physical pairing and the owner's current vehicle grants were outside the audit. [Previous audit](tesla-status-2026-11-19.md)

| Area | Current implementation and gate |
|---|---|
| Account and Collection | Existing OAuth exchange, owner-scoped vehicle cache, encrypted credential rotation and Collection import. The pilot preserves client credentials, callback and signing key. It updates the deployed OAuth function's discovery cache and refreshes the imported vehicle identity. |
| Pairing and setup | Recording control function checks owner, Tesla firmware and compatibility, and signs only the fixed telemetry configuration via the gateway. This branch separates availability, pairing, configuration submission, verification, first telemetry and stream removal. The owner must confirm vehicle adoption after submitting the configuration, before driving. |
| Receiver and consumer | Pinned Tesla receiver terminates mTLS and acknowledges Kafka-backed delivery. A separate consumer commits offsets after the Supabase projection succeeds or a malformed record is classified. The pilot stack has been reviewed statically. Container execution and real Tesla-client TLS are still required. |
| Journey history and household | Existing service-only ingestion and revision-checked projection persist into `activities`. Household access requires explicit future-journey consent and current membership. The app reads the existing feed and groups or reconciles it with iPhone GPS using identity, time and route evidence. The vehicle is the source of a Tesla trip. The app does not infer who drove. |
| Known limits | No historical Tesla import or offline cache for the server feed after app restart. A long outage can split a drive, late evidence can change its reconstructed boundaries, and missing Park can leave an incomplete journey. Existing stable IDs and bounded replay mitigate duplicates. A late merge of two already persisted incomplete fragments still needs a policy before broader rollout. |

## Infrastructure decision

Keep Tesla's official receiver and the existing single-host Kafka package for the first vehicle. An internet-facing receiver that speaks Tesla's authenticated protocol is necessary. The official implementation is the lowest-risk choice because it handles vehicle mTLS, reconnects and protocol acknowledgements. Supabase and the website Worker have separate roles downstream. They cannot serve as drop-in replacements for the receiver. [Tesla Fleet Telemetry](https://developer.tesla.com/docs/fleet-api/fleet-telemetry) · [Official receiver and reliable acknowledgements](https://github.com/teslamotors/fleet-telemetry)

A separate managed Kafka cluster is unnecessary for the pilot. One persistent broker gives acknowledged buffering across consumer restarts and allows replay when Supabase is briefly unavailable. A cheaper existing host is viable if it supports public TCP, persistent encrypted storage, backups and enough memory. Replacing Kafka with a logger or Redis Pub/Sub would sacrifice durable replay. A managed durable dispatcher such as Kinesis or Pub/Sub is an option later, but requires adapting and testing the consumer. It does not remove the need for vehicle mTLS or signing. The single host and replication factor of one leave a host-loss failure mode. Tesla's vehicle-side buffer is bounded. Before expanding, load-test the current per-VIN replay, measure lag and write amplification, and move to incremental or batched reconstruction and replicated storage as needed.

## Cost and approvals

Tesla account linking remains a separate feature. Automatic recording adds an always-on receiver, which can run on suitable infrastructure we already have. A rented VM is an optional budget comparison. Prefer an existing suitable host for the one-car pilot if available.

- A Linux public-IPv4 Lightsail comparison is **US$24/month for 4 GB** or **US$44/month for 8 GB**, before backups, tax, additional Supabase usage and transfer charges. Sydney has a smaller transfer allowance than the headline bundle. Confirm region-specific checkout pricing and capacity before buying. An existing suitable host could eliminate incremental VM spend. [AWS bundle pricing](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-bundles.html) · [Sydney transfer allowances](https://aws.amazon.com/lightsail/pricing/)
- The checked-in signal model estimates about **34,200 signals and US$0.24/vehicle/month before credits** at 60 driving hours and its modeled setup usage. This is an estimate. The pilot's extra setup/removal checks, resend frequency, location changes, and Tesla billing rules can change the total. Tesla documents a $10 monthly discount for eligible developers and small applications. The modeled one-car usage could be fully covered. Verify the account's eligibility, spending cap, payment method and billing currency in the developer portal. No wake calls are required. [Tesla pricing example](https://developer.tesla.com/docs/fleet-api/fleet-telemetry#example-configuration-pricing-analysis) · [Tesla billing and limits](https://developer.tesla.com/docs/fleet-api/billing-and-limits)

## Deployment sequence after approval

1. Approve a single named pilot vehicle, hosting budget, hostname, retention and Tesla API budget. Confirm the registered app, P-256 public key, APAC registration on the North America/Asia-Pacific Fleet audience, exact redirect URI and approved vehicle-data and location scopes. Keep existing OAuth credentials and redirect. [Tesla regions](https://developer.tesla.com/docs/fleet-api/getting-started/regions-countries) · [Tesla virtual keys](https://developer.tesla.com/docs/fleet-api/virtual-keys/overview)
2. Provision an approved Linux host with encrypted persistent storage. Add a DNS-only `fleet.letm3go.au` address. Public 443 must reach the official receiver directly for vehicle mTLS. Public 8443 reaches the authenticated control gateway. Keep Kafka, receiver status/metrics and command proxy private. Mount a public TLS chain and key under the Compose TLS volume, and a separate internal TLS certificate for `command-proxy`. Verify the existing Tesla signing key's public half matches the published key and mount the private key read-only in the signer only. See the existing file ownership, Compose commands and exact Kafka topic creation in the [host setup](tesla-fleet-recording.md#c-receiversigner-pilot-linux-host-with-docker-after-approval).
3. Deploy **`telemetry-ingest`** **`tesla-recording`** and **`tesla`** with the repository's Supabase CLI wrapper against the linked project. Keep gateway JWT verification disabled for these specific handlers as declared in `supabase/config.toml`. Ingestion validates a timestamped HMAC and recording control verifies the caller with Supabase Auth. The two migrations are already present. The `tesla` update is required because the deployed discovery cache omits VINs. Existing account authorizations stay in place. Confirm the update can exchange a callback and refresh the existing discovery cache before enabling streaming.

   ```sh
   npm run supabase -- functions deploy telemetry-ingest --project-ref subobfmlkfqcsaekygat
   npm run supabase -- functions deploy tesla-recording --project-ref subobfmlkfqcsaekygat
   npm run supabase -- functions deploy tesla --project-ref subobfmlkfqcsaekygat
   ```

4. Configure Edge settings `FLEET_INGEST_SECRET`, `FLEET_CONTROL_SECRET` with independent random secrets of at least 32 characters, `FLEET_RECEIVER_HOST=fleet.letm3go.au`, `FLEET_RECEIVER_CA` with the public receiver certificate trust chain, and `FLEET_CONTROL_URL=https://fleet.letm3go.au:8443/configure`. Set `FLEET_VEHICLE_SETUP_APPROVED=false` until the dry run is approved. The recording function also reuses `ACCOUNT_CREDENTIAL_KEY`, `TESLA_CLIENT_ID`, and `TESLA_FLEET_AUDIENCE`. The consumer receives `FLEET_INGEST_SECRET`, `FLEET_INGEST_URL` for the production function, and the Compose-injected `KAFKA_BROKERS`. The gateway receives `FLEET_CONTROL_SECRET` and `FLEET_RECEIVER_HOST`.
5. Run `docker compose config --quiet` and image builds on the approved host. Start Kafka, create the private topics, then start the receiver, consumer and signer/gateway. From outside the host verify the receiver's server certificate with Tesla's official script. In an isolated environment verify production client-cert policy, ingest HMAC rejection, broker persistence, redelivery after consumer restart and recovery after an ingest outage. Verify production shows a fresh ready heartbeat, which checks the receiver status and required consumer topic leaders. Verify the retention job and alerting for heartbeat age, consumer lag, disk, TLS expiry and repeated rejection. A heartbeat is operational evidence only.
6. Once authorized, enable the setup flag. On the selected imported vehicle, open **Automatic recording → Check vehicle setup**. Refresh discovery if the VIN is missing from its cache and update location consent if required. Pair the Letm3go virtual key or follow the legacy vehicle's Safety streaming instruction. Check setup again, explicitly consent and submit. Wait for the vehicle to connect normally, then **Check vehicle setup** to confirm the configured host and port and activate collection. The activation time is the adoption verification time for a new setup. Do not drive before this check, since earlier frames are deliberately excluded.

## Real vehicle acceptance

1. Record the activation timestamp, the healthy heartbeat age, and the verified key and config state. Observe **waiting for telemetry** before the first accepted vehicle data, or verify a redacted post-activation telemetry time if data already arrived.
2. Close Letm3go and turn the pilot iPhone off or leave it behind. Drive a short normal route with a known start and destination and park. Do not handle the phone while driving.
3. From the server, confirm a post-activation receiver event for the pilot vehicle, evidence of advancing committed offsets, a successful projection revision, and **one** persisted Tesla-source drive with plausible start, Park, route and distance. Preserve only redacted evidence. Reopen the iPhone app and check the same activity appears in Trips with Tesla source and the expected vehicle. Reopen again to check the ID and count remain stable.
4. With separately consented test data, verify explicit household access, revoke it, and confirm an overlapping matching iPhone recording reconciles without double-counting. Distinct nonmatching recordings must remain separate. Confirm another account cannot operate the pilot vehicle.
5. Tap **Disable automatic recording**. Confirm ingestion stops immediately, then that Tesla reports a synced empty telemetry configuration. If removal is pending, keep the local stop in effect and retry removal when Tesla is reachable. Verify a subsequent drive creates no new Tesla activity for the disabled binding.

Completion requires the real drive evidence in steps 1–3. The local tests exercise the underlying logic with simulated records and a local database.
